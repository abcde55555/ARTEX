# 安全工作台（Security Workbench）调研与规划

> 本目录是对 [`abcde55555/ARTEX`](https://github.com/abcde55555/ARTEX) 与 [`abcde55555/CodeScan-Artex`](https://github.com/abcde55555/CodeScan-Artex) 两个仓库的调研结论，以及在 ARTEX 基础上构建**统一安全工作台**（渗透测试 / 代码审计 / 逆向分析 / 合规检测）的规划。
>
> 文档性质：研究 + 设计规划，不含实现代码。所有对现状的描述以源码为准并标注 `文件:行`；外部标准/工具信息以公开资料为准，落地前需专业复核。

| 对象 | 版本 | 说明 |
|---|---|---|

## 一页结论

1. **ARTEX 的骨架是可直接复用的核心资产**：LLM 多 agent 编排（planner/worker 双图闭环）、工具审批门（allow/deny/ask + 人工 pending）、全过程留痕（activity + server_logs）、内容寻址证据仓、流量录制、LLM 多 profile 与故障转移——这些机制与「安全能力域」无关，是工作台的底座。
2. **但 ARTEX 的领域模型深度绑定 Web 渗透**：资产只有 6 种网络类型、scope 只是覆盖度分母、findings/报告是漏洞语义、无用户/角色/租户。新增代码审计/逆向/合规能力必须动 **schema + tool + agent** 三层，只加页面不够。
3. **CodeScan-Artex 验证了「能力域 = 工具面收敛」的做法**：它把 agent 工具物理裁剪为 7 个本地文件工具（无 Bash/网络/MCP），并新增 `javadeps` 本地 Java 依赖反编译、复核报文、多账号/部门可见性。这些是代码审计能力最值得移植的部分，但其与 ARTEX 已分叉（151 个文件差异、未 vendored `norma`），**不建议整分支合并**。
4. **四类能力现状差异很大**：渗透测试「已具备，补授权治理」；代码审计「复用度最高，P0 首选」；合规检测「复用度高，规则/模板是主要工作量」；逆向分析「引擎可复用，但工具链与隔离沙箱成本最高」。
5. **工作台的地基不是新功能，而是安全边界**：ARTEX 的 RoE/授权范围机制已被上游移除（`guard/guard.go:4`），当前只有资产黑白名单 + 人工审批。对外提供安全测试服务前必须补：授权书/范围/时间窗、项目级隔离、RBAC、按能力的工具面与沙箱。
6. **最大风险在许可与法务，不在技术**：ARTEX 为 AGPL-3.0（网络服务须提供完整源码），README 另有「仅限本地隔离环境验证、不得对线上系统实际测试」的额外声明；上游停止维护且 `norma` 为闭源后 vendored。工作台若商业化/对外服务，需先解决许可与合规边界。
7. **推荐路线**：P0 平台地基（能力包、项目/授权/RBAC、工具面、统一资产/证据/发现，约 6 周）→ P1 代码审计 + 合规 MVP（约 8 周）→ P2 逆向分析 + 运营化（约 12 周）。代码审计与合规检测法律风险最低、复用度最高，建议作为首批对外演示能力。

## 能力矩阵（摘要）

| 能力域 | 现状 | 可复用来源 | 主要缺口 |
|---|---|---|---|
| 渗透测试 | **已具备** | ARTEX 全链路（双图、worker、流量证据、审批） | 授权/范围强制、工具链（httpx/ffuf/nuclei/sqlmap）、多租户 |
| 代码审计 | **部分具备（可快速移植）** | CodeScan-Artex：只读工具面、`javadeps`、复核报文、多账号 | 代码资产模型、扫描器编排（Semgrep/Trivy/Gitleaks）、代码证据与报告 |
| 逆向分析 | **缺失（引擎可复用）** | ARTEX 编排 + MCP/自定义工具 | 二进制资产模型、反编译/反汇编工具链、隔离执行沙箱 |
| 合规检测 | **缺失（模型可复用）** | 资产图、证据仓、审批留痕、报告 | 控制项/基线模型、核查采集器、合规报告模板 |

## 建议的评审顺序

1. 先读本文「一页结论」与 03 的能力矩阵，确认**目标形态与首批能力**（建议代码审计 + 合规检测）。
2. 评审 04 的六个核心机制，特别是 **§4.5 授权、范围与审批**（地基）与 **§4.6 用户/项目隔离**。
3. 评审 05 的 P0 范围与出口标准，确认人力与排期。
4. 开工前完成 05 §0 的四个决策（产品形态、上游策略、合规边界、LLM 策略）。

## 调研方法与限制

- 两个仓库均以只读方式分析（本地 clone + 源码阅读 + 测试/构建配置检查），**未运行应用、未连接任何真实目标**。
- ARTEX/CodeScan-Artex 的仓库事实均来自源码与 git 历史；外部工具/标准（等保 2.0、密评、Semgrep、Ghidra 等）来自公开资料，具体版本/条款/许可在实现阶段需复核。
- 本文档不构成法律意见；合规检测能力定位为**技术辅助**，正式测评结论须由具备资质的机构出具。
